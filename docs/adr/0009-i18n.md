# ADR 0009 — i18n: namespace tiers, cookie-persisted locale

- Status: accepted
- Date: 2026-04-25

## Context

i18n done badly is a coordination nightmare: every app reinvents the t() function, locale picks reset on cross-zone navigation, and shared labels (currency, dates, common actions) drift in tone across teams.

## Decision

`@raisin/common-i18n` ships:

- An `<I18nProvider app="<name>" appResources={…}>` that wraps `react-i18next`. Apps consume `useT()` and `useLocale()` — they do not import `react-i18next` directly, so a future swap stays a one-package change.
- Two namespace tiers:
  - `global` — shared labels (login/logout, common errors, locale labels). Source of truth lives in this package.
  - `app:<name>` — per-app strings supplied by the app via `appResources`.
  App keys override global keys for the same logical label, so an app can re-skin a shared term without forking the namespace.
- **Cookie-persisted locale**: locale is stored in a cookie scoped to `Path=/`, so switching to `de` on `/app1` keeps German across `/app2` and `/app3`. Without this, every cross-zone navigation would silently reset the language — the worst kind of bug because it looks intermittent.

Locales today: `en` + `de`, intentional for Raisin's DE/UK markets.

## Consequences

- A new app gets translations for shared concepts for free.
- Global terminology evolves in one place.
- The cookie-based persistence is invisible until you remove it; the e2e test pins the behavior.

## Alternatives considered

- **localStorage instead of cookie** — does not survive cross-zone (different origins handled by the gateway behave like the same origin to the user, but localStorage is per-origin per-Next-instance during dev).
- **URL-based locale** (`/de/app1`) — clean but invasive: every app's basePath grows a locale segment and the gateway routing has to match.
- **Per-app i18n libs** — the explicit anti-pattern.
